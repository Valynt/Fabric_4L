# Frontend Query & State Patterns

> **Audience:** Engineers working in [`apps/web/`](../../apps/web/).  
> **Pairs with:** [`DESIGN.md`](../../DESIGN.md) (frontend governance contract).  
> **Source of truth for API shapes:** generated TypeScript client under
> [`apps/web/src/api/generated`](../../apps/web/src/api/generated), regenerated
> from [`contracts/openapi/`](../../contracts/openapi/) via `make contracts`.

This document captures the conventions every new screen, hook, and store in the
web app must follow. The rules exist to keep network behaviour predictable,
caches coherent, and tenant isolation provable end to end.

---

## TanStack Query

### Query key shape

Use a stable tuple of `[domain, resource, filters?]`.

```ts
// Good
useQuery({
  queryKey: ["accounts", accountId],
  queryFn: () => api.accounts.get(accountId),
});

useQuery({
  queryKey: ["accounts", accountId, "signals", { stage }],
  queryFn: () => api.accounts.signals(accountId, { stage }),
});

// Avoid: opaque strings, free-form keys
queryKey: ["account-signals-" + accountId + "-" + stage];
```

Rules:

- The first element is always the top-level domain (`accounts`, `workflows`,
  `benchmarks`, `evidence`, etc.).
- Identifiers come before filter objects.
- Filters must be plain serialisable objects; never functions, classes, or
  Dates without explicit ISO conversion.
- Do not embed tenant IDs in keys — the request context handles tenancy at the
  client and server. Embedding `tenantId` in keys breaks cache reuse on tenant
  switch and risks cross-tenant cache poisoning.

### Mutations

```ts
const mutation = useMutation({
  mutationFn: api.accounts.update,
  onSuccess: (_data, variables) => {
    queryClient.invalidateQueries({ queryKey: ["accounts", variables.id] });
    queryClient.invalidateQueries({ queryKey: ["accounts"] });
  },
});
```

Rules:

- Always invalidate both the detail key and the list-level key.
- Prefer `invalidateQueries` over `setQueryData` unless you have the exact
  response shape and the server is the source of truth (typical case: do not
  use `setQueryData`).
- Do not use `useMutation` for fire-and-forget effects — wrap those in a
  service module that returns a promise and let the component decide whether
  to await.

### Optimistic updates

Allowed only when:

1. The mutation has a known idempotent server side.
2. You implement `onMutate` (snapshot) and `onError` (rollback) symmetrically.
3. You invalidate in `onSettled` to converge on server state.

If those three conditions are not all true, do **not** use optimistic updates.

### Errors and loading

- Render an explicit empty / loading / error state for every query.
- Use the shared `PageShell` and `EmptyState` primitives from
  [`apps/web/src/components/`](../../apps/web/src/components/) — do not roll
  your own card layouts for these states.
- 401 / 403 must be handled by the global query client error handler, not
  per-screen `if (status === 401)` branches.

## Zustand

Zustand is for **transient client UI state** only. Examples that belong in
Zustand:

- Open / closed state of a side panel.
- Local filter selections that are scoped to one workspace and not persisted.
- Multi-step form draft state before submission.

Examples that do **not** belong in Zustand:

- Server data of any kind. Use TanStack Query.
- Authenticated user identity. Use the auth context.
- Tenant context. Use the request / context provider.
- Cross-tab persistent state. Use the URL or server state.

Rules:

- One store per concern; do not create a "god store".
- Selector functions only — never return the entire state from a component
  subscription.
- Co-locate the store with the feature folder that owns it.

## Generated client

- Path: [`apps/web/src/api/generated`](../../apps/web/src/api/generated).
- Regenerated by `make contracts` from `contracts/openapi/`.
- **Never hand-edit** files under `generated/`. Changes are reverted on the
  next regeneration.
- If the generated client lacks an endpoint you need, fix the OpenAPI spec
  first (`contracts/openapi/`), regenerate, then use it. Do not bypass it with
  ad-hoc `fetch` calls.

---

## Tenant safety in the client

- Tenant headers are attached by the request interceptor in
  `apps/web/src/api/`. Application code should never construct them manually.
- Never cache responses keyed by tenant in `localStorage` or `sessionStorage`.
- On tenant switch, the auth layer must clear the query cache
  (`queryClient.clear()`); UI code does not need to do this manually.
