# ADR-040: Data Ownership and System of Record

**Status:** Accepted
**Date:** 2026-07-29
**Deciders:** Platform Architecture Committee
**Reviewers:** Platform Engineering, Layer 4 Engineering, Layer 5 Engineering, Security Team

---

## Context

The Fabric_4L architecture currently has **two competing product data planes** (A-02, Critical):

| Data Plane | Owner | Domain Objects Owned |
|------------|-------|----------------------|
| **Unified API Gateway** (`services/api`) | `api-gateway` | Accounts, Signals, Hypotheses, Evidence, Drivers, ROI Calculations, Value Cases, Context, Governance, Reviews, Benchmarks, Privacy |
| **Layer Services (L1–L6)** | Respective layer owners | Overlapping: Accounts (L4), Hypotheses (L4), Evidence/Signals (L2.5/L4), Value Cases (L4), Benchmarks (L6), Ground Truth (L5) |

The gateway is **not just a reverse proxy** — it independently persists domain objects to its own PostgreSQL/JSONB facade (`services/api/app/core/database.py`). Layer services persist to their own databases.

**Consequences of dual ownership (observed in repository):**
- An account created via gateway `/v1/accounts` may not exist in Layer 4's CRM sync tables
- A hypothesis stored in gateway `/v1/accounts/{id}/hypotheses` was never generated by Layer 4's graph-backed engine
- ROI calculations in gateway `/v1/calculator/roi/calculate` use gateway-local formulas, not Layer 4's benchmarked models
- Value cases rendered from gateway may have no corresponding Ground Truth in Layer 5
- Frontend reads from gateway cache; agents read from layer databases — silent divergence

This is the **highest architectural-drift risk** in the repository: plausible, successful responses without coherent cross-layer lineage.

## Decision

### 1. Single System of Record per Domain Object

| Domain Object | System of Record (Authoritative) | Gateway Role |
|---------------|----------------------------------|--------------|
| **Tenant** | `identity` (shared) | Read-only projection |
| **Account / Prospect** | `layer4-agents` (CRM sync, enrichment) | Gateway CRUD delegates to L4; read model cached |
| **Source / Ingestion Run** | `layer1-ingestion` | Gateway proxies intake; no local persistence |
| **Extraction Job / Entities / RDF** | `layer2-extraction` | Gateway proxies; no local persistence |
| **Knowledge Graph / Value Trees / Entities** | `layer3-knowledge` (Neo4j) | Gateway does not query Neo4j directly |
| **Hypothesis (generated)** | `layer4-agents` (graph-backed generation) | Gateway CRUD delegates to L4; read model cached |
| **Signal / Evidence (extracted)** | `layer2-extraction` (signals) / `layer4-agents` (evidence linking) | Gateway proxies; read model cached |
| **Driver / Value Driver** | `layer4-agents` | Gateway read model only |
| **ROI Calculation / Scenario** | `layer4-agents` (benchmarked formulas) | Gateway proxies `/v1/calculator/*` → L4; no-op |
| **Value Case / Business Case** | `layer4-agents` (orchestrated, grounded, benchmarked) | Gateway `/v1/value-cases/*` delegates to L4 |
| **Ground Truth / TruthObject** | `layer5-ground-truth` | Gateway proxies `/v1/truths/*` → L5 |
| **Benchmark Dataset / Comparison** | `layer6-benchmarks` | Gateway proxies `/v1/benchmarks/*` → L6 |
| **Governance / Review / Audit** | `layer4-agents` (audit orchestrator) | Gateway read model only |
| **Billing / Subscription** | `layer4-agents` (billing domain owned by Layer 4) | Gateway proxies |

**Rule:** The gateway **never** creates, mutates, or authoritatively stores a domain object that has a designated system of record in a layer service. It may only:
- **Delegate** mutating calls to the owning service
- **Cache** read models with explicit TTL and invalidation
- **Aggregate** projections for dashboard/UI consumption (labeled `projection: true`)

### 2. Ownership Contract Enforcement

Every domain object definition (Pydantic model, SQLAlchemy model, OpenAPI schema) **must** declare its system of record:

```python
# Example: services/layer4-agents/src/layer4_agents/models/hypothesis.py
class ValueHypothesis(BaseModel):
    model_config = {"json_schema_extra": {"x-system-of-record": "layer4-agents"}}
    ...
```

The **router contract gate** (`scripts/ci/router_contract_gate.py`) is extended to validate:
- Every mutating route (`POST`, `PATCH`, `PUT`, `DELETE`) on a domain object is owned by the declared system of record
- Gateway routes for that object are either `GET` (read model) or delegate to the owning service

### 3. Gateway Read Models — Explicit, Versioned, Rebuildable

Gateway read models (cached projections) must:
- Be stored in a dedicated schema/namespace (`gateway_read_models`)
- Include `source_of_record`, `source_version`, `projected_at` metadata
- Be rebuildable via `make rebuild-gateway-projections` (idempotent, from layer event streams)
- Have TTL ≤ 24h; invalidation on layer event publication

### 4. Event-Driven Synchronization (Future)

Layer services publish domain events (per ADR-019 event envelope) for:
- `AccountCreated`, `AccountUpdated`
- `HypothesisGenerated`, `HypothesisPromoted`
- `ValueCaseGenerated`, `ValueCaseGrounded`, `ValueCaseBenchmarked`
- `TruthObjectValidated`, `TruthObjectPromoted`
- `BenchmarkComparisonCompleted`

Gateway consumes these to update read models. **Synchronous delegation remains the primary path for mutations**; events are for projection freshness.

### 5. Frontend and Agent Consumers

- **Frontend** reads from gateway `/v1/*` (read models or delegated GETs)
- **Agents (Layer 4 workflows)** read directly from layer databases via repositories
- **Both see the same data** because gateway read models are projections of layer events, not independent writes

## Alternatives Considered

| Alternative | Why Rejected |
|-------------|--------------|
| Gateway as sole system of record (layers become read-only) | Layers own the logic that *produces* the data (extraction, graph reasoning, grounding, benchmarking); gateway cannot replicate this |
| Layers as sole system of record (gateway is pure proxy) | Gateway needs read models for aggregation, dashboards, cross-layer views; pure proxy adds latency for every read |
| Dual write (gateway + layer both persist) | Current state — causes silent divergence; no authoritative source |
| Database-per-service with distributed transactions | Overkill; saga pattern not needed for read-model projection |

## Consequences

### Positive
- **Zero silent divergence** — every domain object has one authoritative writer
- **Gateway scales independently** — read models are lightweight; heavy computation stays in layers
- **Layer autonomy** — layers can evolve schemas, storage, logic without gateway coupling
- **Auditability** — lineage from layer event → gateway projection is traceable
- **Frontend stability** — gateway contract changes only when layer contract changes

### Negative
- **Gateway complexity** — delegation clients, read-model builders, invalidation logic
- **Eventual consistency window** — read models may lag layer writes by seconds (acceptable for UI)
- **Migration effort** — gateway-local tables for Accounts, Hypotheses, Evidence, ROI, Value Cases must be migrated to read models or removed

## Compliance and Migration

### Migration Owner
Platform Engineering + Layer 4 Engineering

### Phased Migration
1. **Phase 0 (this ADR):** Declare systems of record; add `x-system-of-record` to all domain models
2. **Phase 1:** Extend router contract gate to enforce ownership (mutating routes only on owning service)
3. **Phase 2:** Gateway adds delegation clients for each mutating route; gateway-local mutating handlers deprecated
4. **Phase 3:** Gateway read models built for Accounts, Hypotheses, Evidence, Value Cases; TTL + invalidation
5. **Phase 4:** Gateway-local tables dropped; `make rebuild-gateway-projections` verified
6. **Phase 5:** Cross-layer integration test: create via gateway → verify layer has record → verify gateway read model reflects it

### Enforcement Mechanism
- **CI:** Router contract gate validates ownership
- **Schema check:** All domain models must have `x-system-of-record` extension
- **Integration test:** "Write path" test for each domain object (gateway → layer → gateway read model)

### Rollback Strategy
- Gateway delegation can be toggled per-route via feature flag
- Read models can be rebuilt from source events
- Gateway-local tables retained until Phase 5 verified
