## Product

This is the product's differentiating loop: signals and hypotheses are **generated by AI, dispositioned by humans, and only then allowed into the model** (VP-03, VP-04, VP-05; jobs 2; S1 §4.3–4.5).

Correct behavior, normatively:
- Every generated signal/hypothesis is a **candidate** until a human Accepts, Edits, Rejects, or requests customer confirmation (R-3). Generated output never becomes verified, approved, or customer-facing without the human and evidence gates.
- Score composition, evidence coverage, ranking inputs, configuration, run ID, and source version are recorded and shown — not a single opaque confidence number (VP-04).
- Validation and promotion are **separate typed commands with idempotency keys**; action labels correspond to committed backend effects — **Promote** persists a domain artifact, **Convert** creates the promised tree/model (VP-05 eng; UX §5.1.5).
- Promotion creates persistent, idempotent driver-tree and model artifacts with stable IDs and version — not a status flip returning pre-existing IDs (closes GAP-04).
- Workspace generation is non-destructive and version-aware; it never overwrites sibling tab data with empty collections, and speaks one canonical model schema (closes GAP-03).
- Source passage, original generated value, confidence factors, and the human decision are preserved as audit history (R-1, R-2).

L4 orchestrates generation and workflow; L5 owns truth/disposition state; L3 owns tenant-scoped graph retrieval. The frontend presents and dispositions server state — it is never the system of record.

### Inputs / outputs
- **In**: dispositioned signals (J-3 exit); tenant-scoped graph context; generation configuration.
- **Out**: ranked hypothesis candidates with recorded ranking inputs and run ID; human dispositions; on promotion — persistent driver + lever artifacts with stable IDs, model version, lineage to source hypothesis and signal.

### State transitions
- Signal: generated candidate → accepted / edited / rejected / customer-confirmation-requested (only dispositioned signals eligible for hypothesis generation).
- Hypothesis: ranked candidate → validated (human disposition recorded) → promoted (driver artifact persisted). Edit preserves original generated value.
- Operation: `idle -> generating -> idle | retrying`; generation runs resumable, duplicate submissions idempotent.
- Synchronization: `synced | dirty | conflict`; conflicts never silently overwrite another reviewer's disposition.

### Failure modes
- L4 provider timeout/malformed response → generation run marked `degraded` with reason; candidates never auto-accepted; no silent heuristic or mock substitution (R-3, AI-safety rules).
- Validation without required human gate → rejected; AI output cannot self-promote (R-3).
- Promotion replay (retry/duplicate) → same stable driver/model IDs returned (idempotency keys).
- Promotion against a stale hypothesis version → conflict returned with both version identities.
- Graph/query failure during ranking → run fails visibly; no fabricated ranking (R-6 fail-closed on scope uncertainty).

## Verification

**Tests**
- Unit: disposition state machine, idempotency-key replay, command/effect label correspondence, score-composition recording.
- Existing flow tests extended: `HypothesisValidationToDriverFlow.test.tsx`, `EvidenceAcceptanceFlow.test.tsx` against the real promotion contract (GAP-04).
- Integration (real persistence): validate and convert as separate typed commands; promotion creates driver + lever + model version in one idempotent operation; non-destructive workspace regeneration (GAP-03).
- AI evaluation: deterministic invariants on generation (schema, provenance, tool allowlist); LLM-as-judge never sole blocking evidence.
- Browser: hypothesis review → validate → promote journey; reviewer role vs seller role.

**Tenant-isolation assertions**
- Ranking graph queries are tenant-scoped; Tenant A cannot surface, rank, or promote from Tenant B's signals/hypotheses (Neo4j isolation controls under AG-05).
- Foreign hypothesis IDs rejected on validate/promote; denial before data load.
- Review-queue dispositions scoped to tenant + case; audit events name acting tenant only.

**Release gates**
- **AG-02 code-quality-and-tests** — unit/component/integration coverage of the disposition and promotion commands; mutation tests on promotion logic.
- **AG-05 tenant-isolation-and-behavior** — graph/vector retrieval isolation, AI prompt/memory/trace/tool isolation, account-scope enforcement.
- **AG-03 contract-compliance** — hypothesis/driver command schemas versioned; L4↔L5↔L3 cross-layer contract tests.

**Required evidence**
- EV: junit-and-json test-run evidence (candidate-SHA-bound) for disposition + promotion suites.
- EV: cross-layer contract-test results (JSON schema / Pydantic fixtures).
- EV: Playwright traces for the validate→promote browser journey.
- EV: AI-evaluation run record (golden dataset, deterministic assertions) for the generation path.
